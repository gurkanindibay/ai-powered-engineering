# SitePulse Code & Database Flaws Report

Nov 7, 2026 · Gürkan İndibay

## Summary

SitePulse is not safe to run against real residents or real money in its current state. The database schema has been hardened over 12 migrations, but the Rust backend bypasses most of that design: it holds all data in memory, writes to PostgreSQL as a best-effort side effect, and has no working authentication.

Scope: `apps/development-time/SitePulse` (Rust/Axum backend, PostgreSQL schema V1–V12 and `db/init`, Flutter client), plus a lighter pass over AuditGuard, TaskPilot and DevFactory. `COMPLETION_STATUS.md` reports 41/41 stories and 100% complete; the findings below contradict that for anything beyond a demo.

| Severity | Count | Theme |
| --- | --- | --- |
| Critical | 9 | Authentication, authorization, silent data loss |
| High | 12 | Financial correctness, tenancy isolation, integrity |
| Medium | 14 | Schema design, migrations, client, tooling |

The verification harness adds 12 findings of its own (V1–V12, 4 high, 8 medium): its gates cannot fail on the defects above, which is how every task reached COMPLETED. See *Verification harness* and *Harness fix plan* below.

**Remediation status (7 Nov 2026):** 42 of the 47 findings are fixed (✅) and 5 are partly fixed (◐: C7, C9, M1, M6, M12). The *Remediation log* at the end records each change, what remains, and how it was verified. The fixes also exposed one new defect, the Flutter penalty rounding through `double` (see V1), which is fixed. Full local run: all 10 gates of `scripts/run_tests.py` pass.

File paths below are relative to `apps/development-time/SitePulse/` unless stated.

## Critical: security

Anyone who can reach port 8080 can act as any user, including the SaaS admin, and can wipe or rewrite financial data.

## Critical: data integrity

The database is not the system of record. What a user sees and what PostgreSQL holds drift apart, and failures are hidden.

| # | Flaw | Where | Impact |
| --- | --- | --- | --- |
| C7 ◐ | In-memory state is the primary store. All tables are loaded into `Vec`/`HashMap` fields behind one global `RwLock` at startup; writes update memory first, then call the DB with errors discarded (`let _ =` appears 131 times across `db.rs`, `handlers` and services). The codebase has no `transaction()` call, `BEGIN`, or `SELECT … FOR UPDATE`. | `state.rs` 21–50; `main.rs` 25–34; `db.rs`; services | A payment that fails to persist still returns a receipt. Multi-step writes (receipt, entry, allocations, advance) can half-apply. Restart loses anything that only reached memory. Cannot scale past one process. |
| C8 ✅ | Every boot resets two identity sequences to 1: `setval(…'dues_liabilities'…, 1, false)` and the same for `payment_entries`. `init_db` also drops `sites`, `units`, `users`, `persons`, `dues_liabilities` and more if it detects a legacy VARCHAR `sites.id`. | `db.rs` 105–126, 152–166 | After any restart on a non-empty DB, new dues and payment rows hit duplicate-key errors, which are swallowed, so they are silently never saved. |
| C9 ◐ | IDs are strings in Rust (`site-1`, `d-14`, `usr-3fa2b1c9`) and BIGINT in the DB. `parse_id_to_i64` maps them with hard-coded cases (`blok-A` → 1, `usr-site-manager-1` → 2), prefix stripping and a hex fallback; callers then use `unwrap_or(1)` (55 places). `save_user` inserts with an explicit hex-derived id and updates `WHERE id = $1 OR email = $3`. | `db.rs` 48–98, 1221–1300; `payment_tracking_service.rs` 498, 708, 888–889 | Unparseable ids silently write to site 1, unit 1 or dues row 1. Ownership transfer with an unknown previous owner ends person 1's ownership. A hex-id collision overwrites another user's role and password. |

## High: financial logic

The payment waterfall, receipts and accrual produce numbers that cannot be audited and do not match the database.

| # | Flaw | Where | Impact |
| --- | --- | --- | --- |
| H1 ✅ | Payments overwrite the debt. The waterfall does `principal_amount -= pay_principal` and `delay_penalty -= pay_penalty` on the in-memory liability instead of recording paid amounts. The DB model (`paid_principal`, `paid_penalty`) is the opposite. | `payment_tracking_service.rs` 340–375 | The original amount owed is lost in memory; memory and DB disagree after the first payment. |
| H2 ✅ | Penalty payments are never recorded. | H3 ✅ | Receipt numbers race. `next_receipt_number` runs `MAX(sequence_number)+1` before the write lock; two concurrent payments get the same number. The second hits `uq_site_receipt_sequence`, the failure is logged as a warning, and the user still receives the receipt. | `payment_tracking_service.rs` 58–77, 300; `db.rs` 1681–1695 | Issued receipts that do not exist in the DB; duplicated legal receipt numbers on screen. |
| H4 ✅ | In-memory ids are `len() + 1` for receipts and entries. | `payment_tracking_service.rs` 408, 436, 637, 663 | Ids shown to users differ from DB ids; deleting any row causes collisions. |

| H6 ✅ | Advance balance is one number per unit in memory but per (unit, debtor_type) in the DB. The full unit balance is upserted under whichever payer role made the last payment. | same, 520–535; `db.rs` 1867–1889 | Owner and tenant credits get mixed and overwritten. |
| H7 ✅ | The scheduler accrues a hard-coded ₺1,400 for every unit in every site, ignoring `house_types` tariffs and vacancy. ## Database design and tenancy

The schema is mostly well constrained (NUMERIC money, non-negative checks, partial unique indexes for active occupancy and bank accounts), but the core fact tables still lack foreign keys, financial history can be cascade-deleted, and many facts are stored twice.

## Recommended fix order

Fix authentication and the persistence model first; financial fixes on top of the current in-memory design would have to be redone.

1. **Lock the door (C1–C6, M14).** Add real JWT signing and verification (e.g. `jsonwebtoken`) and an Axum auth extractor on every route; derive `site_id`/`unit_id` from the token, not the request. Verify Google ID tokens against Google's keys. Hash with argon2id, delete every plaintext/placeholder comparison and the backdoor passwords, and force a reset of all seeded accounts. Verify webhook HMAC signatures. Move `/system/*` behind a compile-time dev feature.
2. **Make PostgreSQL the system of record (C7–C9).** Remove the in-memory store or reduce it to a cache; switch IDs to `i64` end to end and delete `parse_id_to_i64`; propagate every DB error; wrap each payment in one transaction with `SELECT … FOR UPDATE` on the liabilities. Delete the `setval(…, 1, false)` lines and the legacy `DROP TABLE` branch.
3. **Correct the money flows (H1–H9).** Record allocations instead of mutating principal; write penalty allocations; generate receipt numbers in the DB (per-site counter row updated in the same transaction); respect `debtor_type` and the liability's `expense_type`; price accrual from `house_types`, persist it, and use the site's timezone; add idempotency keys.
4. **Harden the schema (H10–H12, M1–M8).** Add the missing FKs; make ledgers `RESTRICT` with soft delete; drop the duplicated legacy columns; add CHECKs and aggregate invariants; adopt a real migration runner (refinery or sqlx) over the single `migrations/` folder and delete the `db/init` copies.
5. **Clean up delivery (M9–M13).** Replace the Dockerfile with a Rust multi-stage build, move secrets out of compose, bind DB ports to localhost, commit lock files, use HTTPS and a configurable base URL in Flutter, and confine DevFactory's file writes to the sandbox.

An earlier review, `docs/database/DATABASE_DESIGN_REVIEW.md`, covers the schema in more depth. This report adds the application-level findings, which are where most of the risk now sits.

Fix the harness before the application fixes start, so that each application fix is proven by a gate that would have caught the original bug. Phase 0 is the urgent one: until it lands, every green result is unreliable.
